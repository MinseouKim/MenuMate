## 1. 결과 파일 형식 (`backend/engine/menu-features.json`)
Backend `engine.ts`(parseEngine)와 합의한 형식이다. 실제 파서로 읽히는 것을 확인했다 (Backend `1f025fd`).

```jsonc
{
  "engineVersion": "2026-10-27-v1",          // 만든 날짜-v번호
  "generatedAt": "2026-10-27T...+09:00",
  "weights": { "ageFit": 3, "reputation": 1.5 }, // 점수 가중치 (questions.md v2, D82). Backend는 이 값을 읽는다
  "sources": [{ "name", "url", "license" }],   // 출처 표시 (KR3는 CC BY-NC-SA)
  "menus": [{
    "menuId": "m001", "menuName": "된장찌개",
    "features": { "spicy", "mild", "soup", "soft", "hearty", "light" },  // 0~1
    "ageFit": { "under35", "35to54", "55plus" },                         // 0~1, 0.5 중립
    "reputation": 0.64,                                                    // 0~1, 0.5 중립
    "reviewCount": 3723,      // 계산에 쓴 리뷰 수 (광고 제외)
    "adFilteredCount": 3,     // 광고·복사로 걸러진 리뷰 수
    "ageFitBasis": "stats",   // "stats" | "rule". 추천 이유 age_fit은 "stats"일 때만 (D82)
    "evidence": { ... }       // 설명용. Backend는 읽지 않음
  }]
}
```
- 리뷰가 `MIN_REVIEWS`(20)개 미만인 메뉴는 파일에서 뺀다. Backend는 빠진 메뉴를 v1 점수로 계산한다. 지금은 26개 모두 들어 있다.
- `light`(담백함)는 questions v2에서 쓸 새 특징이다. 승인 전에는 Backend가 모르는 키라 무시한다.

## 2. 메뉴 특징 (`features.py`, `menus.py`)
1. **메뉴 찾기**: 동의어 표(`menus.py`)로 리뷰 속 메뉴를 찾는다. 예: 순댓국·순대국 → 순대국밥, 엘에이 갈비 → LA갈비, 평양냉면 → 물냉면. 긴 이름이 짧은 이름으로 세지지 않게 했다(돌솥비빔밥 ≠ 비빔밥, 비빔냉면 ≠ 물냉면, 김치전골 ≠ 김치전). 배달앱 리뷰는 주문한 메뉴(`Menu` 열)도 쓴다.
2. **근거 글**: 메뉴명이 나온 곳의 앞 10자와 뒤 40자만 본다. 다른 메뉴명이 나오면 거기서 끊는다. 마침표 없이 긴 리뷰에서 다른 음식의 맛 표현이 섞이는 것을 막기 위해서다(처음엔 문장 단위로 셌는데 김치찌개가 된장찌개보다 덜 맵게 나왔다). 배달 리뷰에 메뉴명이 없고 주문 메뉴가 하나면 리뷰 전체를 그 메뉴의 근거로 쓴다.
3. **맛 표현 세기**: 근거 글마다 특징별 긍정·부정 표현이 있는지 센다.

| 특징 | 긍정 표현 | 부정 표현 |
|------|-----------|-----------|
| spicy 매운맛 | 맵·매콤·얼큰·칼칼·화끈·청양 | 안 맵·맵지 않·덜 맵 (긍정에서 뺌) |
| mild 순한맛 | 순하·슴슴·안 맵·자극적이지 않 + 매운맛 부정 − 매운맛 긍정 | |
| soup 국물 | 국물·육수·뜨끈·얼큰·진국·사골·해장 | 국물이 없·적 |
| soft 부드러움 | 부드럽·야들·촉촉·말랑·연하·살살 녹·술술·폭신 | 질기·딱딱·뻣뻣·퍽퍽 |
| hearty 든든함 | 든든·푸짐·양이 많·배부르·넉넉 | 양이 적·부족·감질 |
| light 담백함 | 담백·깔끔·슴슴·싱겁·짜지 않 | 짜(진짜·짜장 제외)·짭짤·간이 세·자극적·느끼·기름지 |

4. **0~1로 바꾸기**: `비율 = (긍정 − 부정) / 근거 글 수`. 근거 글이 20개 이상인 메뉴들의 10~90 백분위를 0~1로 둔다.
   - `리뷰값 = w·비율 + (1−w)·사전값`, `w = n/(n+40)`
   - `특징값 = 0.5·사전값 + 0.5·리뷰값`
   - 사전값은 메뉴 태그(v1)에 있으면 0.8, 없으면 0.2, light는 0.5다. 리뷰는 "얼마나 자주 말하는가"를 보여 준다. 그래서 국물·부드러움처럼 음식 자체의 성질은 덜 말해질 수 있어, 사전값을 절반 남긴다(처음엔 된장찌개 국물이 0.12로 나왔다).

## 3. 평판과 연령대 적합도 (`signals.py`)

### 평판 (0~1, 0.5 중립)
- 긍정·부정: KR3는 평점(1 긍정, 0 부정, 2 애매는 제외). 배달앱은 맛 별점(4~5 긍정, 1~2 부정, 3 제외)이고, 제작자가 "리뷰 이벤트 영향 없음"(`BiasFree`=1)으로 표시한 리뷰만 쓴다.
- 데이터마다: `p = (긍정 + 50·전체긍정률) / (리뷰 수 + 50)`, `평판 = sigmoid(2·(logit p − logit 전체긍정률))`. 전체 평균과 같으면 0.5이고, 리뷰가 적으면 0.5 쪽으로 간다. 두 데이터의 값을 리뷰 수로 가중 평균한다.
- 한계: 같은 메뉴라도 **식당이 달라서** 생기는 차이가 섞여 있다. 메뉴 자체의 평판이라기보다 "그 메뉴를 먹은 손님들의 만족도"다.

### 연령대 적합도 (0~1, 0.5 중립)
나이가 붙은 리뷰가 없다(datasets.md). 그래서 두 근거를 섞는다.
1. **통계 — 국민건강영양조사(KNHANES) 2024 24시간 회상 원시자료** (`knhanes.py`, 지금 쓰는 것)
   - 파일 `HN24_24RC.sav` 하나에 개인 ID, 나이(`age`), 영양조사 가중치(`wt_ntr`), 음식명(`N_DNAME`)이 모두 있다 (543,782행, 6,802명). 기본DB(HN24_ALL)는 필요 없다.
   - 음식명을 메뉴 26개에 잇는다 (`DISH_RULES`). 예: 돼지고기김치찌개 → 김치찌개, 순대국 → 순대국밥, 달걀말이 → 계란말이밥, 제육볶음 → 제육덮밥. 사발면·컵라면·버거·피자·삼각김밥처럼 다른 음식에 섞인 이름은 뺀다.
   - 연령대는 키오스크와 같다: under35 = 19~34세(995명), 35to54(1,793명), 55plus = 55세 이상(3,068명, 65세 이상 1,895명 포함). 19세 미만은 뺀다.
   - 섭취 비율 = 조사 하루 동안 그 메뉴를 한 번이라도 먹은 사람의 가중 비율 (가중치 `wt_ntr`)
   - `적합도 = 0.5 + 0.5·log2(그 연령대 비율 / 세 연령대 평균)`. 섭취자 n명이면 `0.5 + (적합도 − 0.5)·n/(n+30)`로 0.5 쪽에 당긴다. **19세 이상 섭취자가 30명 미만이면 통계를 쓰지 않는다** (돼지국밥 4명, 콩나물국밥 18명, 돌솥비빔밥 14명, LA갈비 21명).
   - 결과 파일에는 연령대별 집계값에서 나온 적합도만 들어간다. 개인 자료나 ID는 없다 (확인함).
   - 원시자료 위치: `ai/engine/data/knhanes/` (git 제외). 없으면 아래 국민영양통계로 계산한다.
1-b. **통계 — 국민영양통계 다빈도음식** (KNHANES가 없을 때만 쓰는 예비) (국민영양통계 다빈도음식, 2020~2023): 연령층별로 그 음식을 먹은 사람 비율이다.
   - 상위 100개만 있어서, 빠진 칸은 그 칸의 100위 비율 × 0.8로 채운다.
   - 연령대 섞기: under35 = 0.75·(19~29세) + 0.25·(30~49세), 35to54 = 0.6·(30~49세) + 0.4·(50~64세), 55plus = 50~64세. CSV에 65세 이상이 없어 50~64세로 대신한다.
   - `적합도 = 0.5 + 0.5·log2(그 연령대 비율 / 세 연령대 평균)`. 평균의 2배면 1, 절반이면 0이다.
   - 관찰된 칸이 6개 미만인 음식(순두부찌개, 물냉면 등)은 통계를 쓰지 않는다.
2. **규칙** (특징 × 연령대 가중치): `0.5 + Σ 가중치 × (특징 − 0.5)`.
   - 55plus: 국물 +0.15, 부드러움 +0.20, 순함 +0.15, 담백 +0.15, 매운맛 −0.15, 든든함 −0.05
   - under35: 매운맛 +0.20, 든든함 +0.15, 부드러움 −0.10, 순함 −0.10, 국물 −0.05, 담백 −0.05
   - 35to54: **규칙 없음** (D81, 아래)
   - 근거: 고령층 식사 지침(부드럽고 덜 자극적인 음식)과 통계의 방향. 통계가 있는 메뉴 9개로 확인하면 규칙과 통계의 상관이 under35 0.58, 55plus 0.47이다.
3. **섞기**: under35·55plus는 통계가 있으면 `0.7·통계 + 0.3·규칙`, 없으면 규칙만이다. **35to54는 통계가 있으면 통계만, 없으면 0.5** (D81).
   - KNHANES 2024 기준으로 통계가 있는 메뉴는 **22개**(국민영양통계 때는 9개), 규칙만 쓰는 메뉴는 4개다.
   - 규칙과 KNHANES 통계의 상관(22개 메뉴): under35 0.47, 55plus 0.43. 국민영양통계 9개 때(0.58, 0.47)와 비슷해 규칙의 방향은 맞다.

## 4. 광고성 리뷰 필터 (D75)

### 4.1 1단계 규칙 (`menumate_engine/ad_filter.py`)
글쓴이 **본인이 대가를 받았다고 밝힌 리뷰**와 **복사해 붙인 리뷰**를 거른다.

| 코드 | 걸리는 것 | 걸리지 않게 한 것 (오탐 방지) |
|------|-----------|------------------------------|
| `sponsored` | 체험단으로·체험단이지만, 협찬으로 방문·협찬 받, 제품 협찬, 글 첫머리 "협찬", #협찬 #광고, 원고료, 소정의 지원금, 업체로부터 … 제공, 식사권·식사를 제공받, 무상 제공, 제공받아 작성, 서포터즈 | "협찬 아님", "협찬 안 받았", "내돈내산", "경쟁업체", "근처 업체", "블로그가 다 체험단 글", "광고글처럼" |
| `review_event` | 리뷰 이벤트(로 받은·참여), 리뷰 약속, 별5 약속, 이벤트 참여해서·참여합니다, 리뷰 쓰고 … 받았, **배달앱 주문 옵션의 리뷰 이벤트 선택**(가려 쓴 글자 "Z1뷰 OI벤트", "ㄹㅣ뷰약속" 포함) | "리뷰 이벤트가 없어서", "다 리뷰 이벤트니까", "리뷰 이벤트 때 말고는", "명함 이벤트", 옵션 "선택안함" |
| `repeated_sentence` | 같은 문장(공백 빼고 6글자 이상)이 한 리뷰에 3번 이상 | "미안하다"처럼 짧은 말버릇 |

| ② 배달앱 | 128,668 | 약 5,570 | 글에서 2,036 (review_event 2,032), 주문 옵션에서만 3,534 |

### 4.2 표본 정확도 (걸러진 리뷰 표본, AI가 한 건씩 판정)
판정 기준:
- **엄격**: 글쓴이가 대가(무료 음식, 식사권, 원고료, 리뷰 이벤트 혜택)를 받았거나 받으려고 쓴 것이 글이나 주문 기록으로 확인될 때만 정답
- **넓게**: 엄격 + 리뷰 이벤트 혜택을 홍보하는 글("리뷰 이벤트 하면 음료 줘요")

| 회차 | 표본 | 엄격 정밀도 | 비고 |
|------|------|-------------|------|
| 1차 규칙 | 100 (KR3 규칙 50, KR3 복사 15, 배달 글 20, 배달 옵션 15) | **61%** (판단 가능 85개 중 52) | KR3 규칙 38%(19/50), 배달 글 90%(18/20), 배달 옵션 100%(15/15), 복사 리뷰 15개는 판단 불가(템플릿 문장) |
| 2차 규칙 (오탐 유형 수정 후, **새 표본**) | 98 (KR3 규칙 58 = 남은 후보 전부, 배달 글 25, 배달 옵션 15) | **59%** (58/98), 넓게 69% (68/98) | KR3 규칙 40%(23/58), 넓게 57%(33/58) · 배달 글 84%(21/25) · 배달 옵션 93%(14/15) |

1차 오탐 유형(업체 언급, 부정 표현, 남의 광고 언급, 짧은 말 반복)은 2차에서 사라졌다. 2차에 남은 오탐은 대부분 **KR3의 "리뷰 이벤트" 언급 글**이다. 예: 평점이 리뷰 이벤트로 부풀려졌다고 비판하는 글, 이벤트가 있다고 안내만 하는 글. 2차에서 찾은 쉬운 오탐 2가지("선택안함" 옵션, "협찬 안 받았고요")는 고쳐서 테스트로 고정했다. 다만 이 수정 뒤의 정확도는 다시 재지 않았다. 표본에 맞춰 계속 고치면 과적합되기 때문이다.

**판정은 사람이 아니라 AI(이 세션)가 했다.** 표본 원문은 라이선스 때문에 커밋하지 않고 `ai/engine/out/`(git 제외)에만 둔다.

### 4.3 2단계 분류 모델 (`menumate_engine/ad_model.py`)
- 학습 데이터: ② 배달앱 리뷰의 `BiasFree` 라벨 (0 = 리뷰 이벤트 영향 92,318건, 1 = 영향 없음 34,435건, 3은 의미 미상이라 제외)
- 모델: 글자 2~4-gram TF-IDF + 로지스틱 회귀, **식당 단위로 나눈** 평가 (학습 86,225 / 평가 40,528)

| AUC | 정확도 | 정밀도 | 재현율 | 평가셋 양성 비율 |
|-----|--------|--------|--------|------------------|
| 0.674 | 0.657 | 0.797 | 0.707 | 0.724 |

**결론: 필터로 쓰지 않는다.** 정확도가 "모두 광고라고 답하기"(0.724)보다 낮다. 모델이 배운 단서도 광고 표현이 아니라 "사진 못 찍었어요" 같은 사진 관련 표현이다. 이 라벨은 글 내용이 아니라 **별점 5점 + 사진 첨부 여부**로 붙인 것이라, 글에서 배울 신호가 거의 없다. KR3에 적용하면 평범한 리뷰를 대량으로 지울 위험이 있다.

### 4.4 엔진에서의 쓰임
- 1단계 규칙이나 복사 리뷰로 걸린 리뷰는 **특징·평판 계산에서 모두 뺀다.** 메뉴별 `adFilteredCount`가 이 수다.
- ② 배달앱 리뷰의 평판은 데이터 제작자가 "영향 없음"(`BiasFree` = 1)으로 표시한 리뷰의 맛 별점만 쓴다. 리뷰 이벤트 리뷰는 92%가 별점 5점이라 평판 정보가 없다. 대신 특징(맵다, 짜다 등) 계산에는 쓴다.

### 4.5 한계
- KR3 규칙의 정밀도는 약 40%로 낮다. 다만 64만 건 중 76건만 걸러지므로 엔진에 주는 영향은 매우 작다(0.01%).
- 재현율(놓친 광고)은 재지 않았다. 체험단을 밝히지 않은 광고는 규칙으로 잡을 수 없다.
- 배달앱 표시 데이터는 "체험단·협찬"이 아니라 "리뷰 이벤트"만 다룬다.

## 6. 한계 (전시 설명용)
- **35~54세 연령대 적합도는 규칙을 쓰지 않는다 (D81, 2026-10-27).** 처음 넣은 규칙(국물·든든함 +)은 통계와 반대 방향이었다(상관 −0.48). 그대로 쓰면 이 연령대에 틀린 추천을 할 수 있다. 그래서 통계가 있는 9개 메뉴는 통계만 쓰고, 나머지 17개는 중립(0.5)으로 둔다. 통계가 없는 메뉴에서는 35~54세 손님의 추천이 취향 답과 평판으로만 정해진다.
- **나이 정보가 붙은 리뷰가 없다.** 연령대 적합도는 "그 연령층이 실제로 자주 먹는 음식"(공공 통계)과 규칙의 조합이다. "비슷한 연령대 손님의 평"이 아니다.
- 연령대 통계는 KNHANES **2024년 한 해**(6,802명)뿐이다. 메뉴별 섭취자는 30~600명이라 연령대별로는 수십 명인 메뉴가 많다(예: 오징어덮밥 under35 2명). 0.5 쪽으로 당기기는 하지만 흔들림이 있다. 2022·2023년을 더하면 표본이 약 3배가 된다.
- 26개 중 4개 메뉴(돼지국밥, 콩나물국밥, 돌솥비빔밥, LA갈비)는 섭취자가 적어 규칙만 쓴다.
- 특징값은 리뷰 표현의 **상대 비교**다. 26개 메뉴 안에서 "더 맵다·덜 맵다"이지, 절대적인 맵기 단계가 아니다. 메뉴가 바뀌면 값도 바뀐다.

- 리뷰가 적은 메뉴(두부부침 107, 돌솥비빔밥 138, LA갈비 158, 호박죽 130)는 사전값(메뉴 태그)에 가깝다.
