# 질문 v2 (D76) — 승인됨 (D82)

- 작성: AI / 상태: **승인 (2026-10-27, D82)**. 계약 원문은 [`docs/contracts/questions.md`](../../docs/contracts/questions.md) v2에 합쳤다. 이 문서는 근거와 시뮬레이션 기록이다.
- 승인 때 바뀐 점: priority 계수 1.5 → **0.5** (아래 3장 재시뮬레이션)
- 근거: 엔진 특징값 [`engine.md`](engine.md), 결과 파일 `backend/engine/menu-features.json`

## 1. 원칙
- 질문은 **5개**, 답은 `yes` / `no` / `skip` 그대로 (D76). "그냥 메뉴 볼래요"도 그대로 (D17).
- 짧은 문장. 씹는 능력·건강·나이를 캐묻는 느낌이 나지 않게 "좋으세요?"로 취향만 묻는다.
- 55세 이상/미만 모두 같은 질문, 같은 점수 (D19). 연령대는 서버로 보내지 않는다 (D73). 연령대 점수는 서버가 세 연령대 결과를 모두 계산할 때만 쓴다.
- 질문 1~4는 v1.1과 같은 id·같은 점수다. 5번 하나만 새로 넣는다. 그래서 v1 프론트와 TTS가 그대로 동작한다.

## 2. 질문과 점수표

| 순서 | id | 화면/음성 문구 | yes | no | 바뀐 점 |
|------|----|---------------|-----|----|---------|
| 1 | `q_spicy` | 매운 음식도 괜찮으세요? | spicy +2, mild −1 | spicy −3, mild +1 | 없음 |
| 2 | `q_soup` | 따뜻한 국물 요리가 좋으세요? | soup +2 | soup −1 | 문구만 짧게 ("…국물이 있는 음식이…" → "…국물 요리가…") |
| 3 | `q_soft` | 부드러운 음식이 좋으세요? | soft +2 | (변화 없음) | 없음 (v1.1) |
| 4 | `q_hearty` | 든든하게 드시고 싶으세요? | hearty +2 | hearty −1 | 없음 |
| 5 | `q_light` **새로** | 담백한 맛이 좋으세요? | light +2 | light −1 | 엔진의 담백함(짜지 않음·깔끔함) 특징에 맞춘 질문 |

- `skip`은 영향 없음.
- 5번을 고른 이유: 엔진이 뽑는 특징 6개 중 질문이 없던 것이 담백함뿐이다. "짜지 않은 음식"은 건강(염분)을 묻는 것처럼 들려서 "담백한 맛"으로 했다. "아니요"는 진한 맛을 좋아한다는 뜻으로 보고 −1만 준다.
- 질문 수는 4개 → 5개다. 사용성 테스트(D66)에서 너무 길다고 하면 5번을 빼도 점수 계산은 그대로 동작한다.

## 3. 점수 계산 (Backend 구현, v2-changes 3장)

```
prefs[f]    = 답 점수를 특징별로 더한 값
score(menu) = Σ prefs[f] × feature[f]                 (feature: 엔진 특징값 0~1)
            + W_age × (ageFit[band] − 0.5)            (연령대별 결과에만. items(unknown)에는 0)
            + W_rep × (reputation − 0.5)
            + priority × 1.5
```

**가중치: `W_age = 3`, `W_rep = 1.5`** (승인, 엔진 파일 `weights`에 반영)
- 취향 점수의 폭(약 ±2~4)이 가장 크고, 연령대(±0.6)와 평판(±0.4)은 비슷한 메뉴 사이에서 순서를 바꾸는 정도로 둔다.
- 평판은 같은 메뉴라도 식당 차이가 섞여 있어(engine.md 3장) 연령대보다 작게 둔다.
- 엔진에 없는 메뉴는 v1 그대로 계산한다 (feature = 태그 1/0, 연령대·평판 중립).

## 4. 추천 이유 (`reasons`) 코드와 화면 문구

| reason | 문구 | 붙이는 조건 (Backend) |
|--------|------|----------------------|
| `spicy` | 매콤한 맛 | prefs[spicy] > 0 이고 feature[spicy] ≥ 0.5 |
| `mild` | 순한 맛 | prefs[mild] > 0 이고 feature[mild] ≥ 0.5 |
| `soup` | 따뜻한 국물 | 위와 같은 방식 |
| `soft` | 부드러운 식감 | 위와 같은 방식 |
| `hearty` | 든든한 한 끼 | 위와 같은 방식 |
| `light` **새로** | 담백한 맛 | 위와 같은 방식 |
| `age_fit` **새로** | 또래 분들이 자주 드세요 | 연령대별 결과이고, ageFit[band] ≥ 0.6이고, 그 메뉴의 `ageFitBasis`가 `"stats"`일 때만 |
| `review_good` **새로** | 손님 평이 좋아요 | reputation ≥ 0.70 이고 reviewCount ≥ 100 |
| `store_pick` | 사장님 추천 | priority > 0 (v1과 같음) |

- 순서: 특징 이유(기여가 큰 순) → `age_fit` → `review_good` → `store_pick`. 화면에는 앞에서 2~3개만 보여 주기를 권한다 (Frontend 판단).
- **특징 이유에 `feature ≥ 0.5` 조건을 새로 둔다.** v1은 태그가 1/0이라 필요 없었다. v2는 특징이 0~1이라 조건이 없으면 매운맛 0.1인 메뉴에도 "매콤한 맛"이 붙는다.
- **`age_fit`은 통계 근거가 있는 메뉴에만 붙인다.** 나이가 붙은 리뷰가 없으므로 "또래 손님이 좋아해요"라고 하지 않고, 공공 통계(그 연령층이 실제로 자주 먹는 음식)에 맞는 "자주 드세요"로 썼다. 규칙만으로 만든 적합도는 점수에는 쓰지만 이유로 보여 주지 않는다. 이를 위해 엔진 파일 메뉴마다 `"ageFitBasis": "stats" | "rule"`을 새로 넣는다 (Backend가 읽어야 함). 지금 값으로 이 이유가 붙는 경우는 55세 이상의 된장찌개(0.62)·콩나물국밥(0.65)·잔치국수(0.63)다.
- 지금 값으로 `review_good`이 붙는 메뉴: 육개장, 콩나물국밥, 오징어덮밥, 비빔국수, 수제비, 두부부침 (0.70 이상, 리뷰 100개 이상).

| 누가 | 무엇 |
|------|------|
| AI | 엔진 파일 weights를 3 / 1.5로, 메뉴마다 `ageFitBasis` 추가, `engine.md` 갱신 |
| Backend | `q_light` 추가, `q_soup` 문구, 특징 키에 `light` 추가, reasons 규칙(조건·새 코드 3개), `ageFitBasis` 읽기 |
| Frontend | 이유 문구 3개(`light`, `age_fit`, `review_good`) 추가. 질문은 `GET /api/questions`로 받으므로 화면 코드 수정은 없음 |
| AI (완료) | `docs/contracts/questions.md` v2로 합침 (PM 지시, 이번 한 번) |
| Backend | priority 계수 1.5 → 0.5 |
