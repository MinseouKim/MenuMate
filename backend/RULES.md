# Backend 규칙

기준 문서: [`docs/00_pm_decisions.md`](../docs/00_pm_decisions.md). 이 문서와 충돌하면 PM 결정이 우선한다. 괄호 안 번호(D00)는 그 문서의 결정 번호다.

## 1. 담당 산출물
1. **DB ERD**
2. **API 서버**와 더미 메뉴 시드
3. **결제 시뮬레이션** (D13)
4. 주관 계약: `docs/contracts/menu-schema` (메뉴 JSON 스키마), `docs/contracts/api` (API 명세)
5. 공동 작업: 환경 변수 관리 가이드의 DB 접속정보, 시스템 아키텍처 구상도의 서버 부분

## 2. 기술 스택 (D36)
- Node.js + TypeScript + Fastify
- ORM: Prisma
- DB: SQLite (파일 하나). 나중에 PostgreSQL로 바꿀 수 있게 SQLite 전용 기능을 쓰지 않는다.
- API 타입은 프론트와 공유할 수 있게 TypeScript 타입으로 내보낸다.

## 3. 실행 환경 (D32, D22)
- 프론트, 서버, DB가 **같은 노트북에서 인터넷 없이** 동작해야 한다.
- 외부 API, 클라우드 DB, 외부 인증을 쓰지 않는다.
- Mac에서 개발하고 나중에 gram(Windows)으로 옮긴다. 경로 구분자, 줄바꿈, 셸 스크립트처럼 OS에 따라 달라지는 코드를 피한다. 실행 스크립트는 `npm run`으로 통일한다.

## 4. 메뉴 데이터 (D7, D12, D33)
- 더미 메뉴와 우루루 실데이터 JSON은 **같은 스키마**를 쓴다. 스키마를 먼저 확정한다.
- 최소 필드: 메뉴명, 가격, 카테고리, 사진 경로. 추천을 위해 취향 태그(`spicy`, `soup`, `soft`, `hearty`, `mild` 등)와 `priority`를 둔다.
- 사진은 서버가 로컬 파일로 제공한다 (인터넷 없이).
- 실데이터가 10/31(토)까지 오면 시드 스크립트로 교체한다. 오지 않으면 더미로 전시한다.

## 5. DB 규칙 (D2, D6, D26)
- 얼굴 이미지, 원본 추정 나이, 임베딩 등 생체 정보는 **어떤 테이블에도** 저장하지 않는다.
- 연령대도 저장하지 않는다. 주문 테이블에 `55세 이상/미만` 같은 값을 넣지 않는다. 필요하면 PM 승인을 먼저 받는다.
- 저장하는 것: 메뉴, 카테고리, 태그, 주문(매장/포장, 주문번호), 주문 항목(수량), 결제 시뮬레이션 결과.
- 메뉴 옵션(맵기, 추가 메뉴)은 범위 밖이다.
- 관리자 페이지는 만들지 않는다. 메뉴 `priority` 컬럼만 두어 나중에 붙일 수 있게 한다.
- 금액은 정수(원 단위)로 저장한다. 부동소수점 금지.
- 스키마 변경은 Prisma 마이그레이션으로 남긴다.

## 6. API 규칙
- 요청·응답 필드는 `docs/contracts/api`에 있는 것만 쓴다. 바꿀 때는 Frontend, AI에게 알리고 PM 승인을 받는다 (D37).
- **추천** (D5, D19): 질문 4개의 답 → 태그 점수 + 메뉴 `priority` → 상위 3개. 55세 이상/미만 모두 같은 규칙이다. 응답에 점수를 포함해 왜 추천됐는지 설명할 수 있게 한다. 질문 목록은 `docs/contracts/questions`를 따른다.
- **결제** (D13): `pay(order) → success | fail` 인터페이스 뒤에 시뮬레이션 구현체를 둔다. 나중에 PG나 단말기로 교체한다. 실패 시에도 주문 내용은 유지한다.
- **주문번호**: 결제 성공 시 발급한다. 하루 단위로 짧게(예: 3자리) 읽기 쉽게 만든다. 형식은 계약에서 확정한다.
- 에러 응답에는 코드와 화면에 바로 띄울 수 있는 사용자용 한국어 메시지를 함께 준다.

## 7. 환경 변수와 보안
- DB 경로 등 설정은 `.env`에서만 읽는다. `.env`는 커밋하지 않고 키 이름만 담은 `.env.example`을 커밋한다.
- 외부 API 키는 현재 필요 없다. 새 외부 서비스가 필요해지면 PM에게 먼저 묻는다.
- 로그에 얼굴 데이터나 개인 식별 정보를 남기지 않는다.
