# 말로 추천 v2: 핸즈프리 대화·대화 기반 추천 설계 (2026-11-03)

작성: 팀 합의안. Yum(음성 AI, Byte by Yum! 방식), AI 개발자, 프론트 개발자가 각자 제안한 뒤 한 번 교차 검토함. 정리·최종 판단: 리드.

## 1. 왜 하는가 (팀장이 직접 써 보고 지적한 것)
1. 첫인사가 가게와 상관없음 ("비 오는 저녁이네요, 따뜻한 국물 어떠세요?")
2. "눌러서 대답하기"가 불편 (눌러서 시작하고, 다 말한 뒤 한 번 더 눌러야 끝남)
3. AI 대답이 느려 대화가 끊김
4. 추천이 대화 내용을 바탕으로 하지 않는 것 같음
5. 요청: 손님이 말하면 직원 음성이 즉시 멈추고 듣기로 전환(barge-in). 친근하고 주고받는 화면으로 주문 시간 단축. 추천 화면 깔끔하게.

| 지적 | 원인 (파일:줄) |

| 2 | 말을 끝내는 신호가 버튼밖에 없음 (`useSpeechInput.ts:39-43,80`). 인식 결과도 끝날 때 한 번만 넘김 (`webSpeechSttProvider.ts:53`) |

| 숨은 버그 | 서버 답을 기다리는 중에 손님이 말하면 확인 화면으로 넘어가 버림 (`useKiosk.ts:197`) |
| 숨은 버그 | picks 검증이 품절 메뉴를 걸러내지 못함 (`chat.ts:194`, `menuKnowledge.ts:73`) |

## 3. 목표 / 하지 않을 것
- **목표**: 손님이 말을 마친 뒤 첫 소리(맞장구)까지 0.3초 이내, 의미 있는 대답 p50 1.5초·p95 3초. 시작부터 담기까지 중앙값 45초 이하, 터치 2번(시작, 담기). 1순위 추천은 직원 AI가 대화로 고른 메뉴.
- **하지 않을 것 (1차)**: SSE 스트리밍, 마이크 소리를 따로 분석하는 별도 VAD와 볼륨 낮추기(ducking), 모델 파인튜닝, GPU가 필요한 Riva, 메뉴 목록을 턴별로 나누기, mood를 점수에 반영.
- **실패로 볼 것**: 스피커에서 나온 직원 목소리를 손님 말로 착각해 혼자 대화가 이어지는 경우. 알레르기·제외 재료를 어긴 메뉴가 1순위에 오르는 경우.

## 4. 설계

### 4-1. 대화 흐름 (프론트)
- **첫인사**: 화면이 서버를 기다리지 않고 바로 띄웁니다. "우루루 평촌본점에 어서 오세요! 몇 분이서 오셨어요?" 문구는 `chatTemplates.ts` 한 곳에만 두고, 기록에는 assistant 턴으로 넣습니다. 서버는 첫인사를 만들지 않습니다. 날씨는 추천 이유에만 씁니다.
- **핸즈프리**: 대화 화면에 들어오면 마이크를 계속 켭니다. 브라우저 인식이 끝나면(onEnd) 자동으로 다시 시작합니다. 화면을 떠나면 끕니다.
  - 말끝 감지: 중간 인식 결과가 멈춘 뒤 어미가 "요/주세요/이요"면 500ms, "그리고/음/어"면 1,200ms, 그 밖은 800ms 기다립니다. 큰 글씨 모드는 +500ms입니다. 값은 설정으로 둡니다.
  - 한 번 듣는 시간은 최대 8초입니다.
- **barge-in (1차 최소 세트)**
  - 직원이 말하는 동안에도 인식을 켜 둡니다. 중간 인식 결과가 지금 읽는 문장과 2자 넘게 다르면 `stopSpeaking()`으로 멈추고, 300ms 안에 "듣고 있어요"로 바꿉니다.
  - 화면 아무 곳이나 누르면 즉시 멈춥니다.
  - 끊긴 직원 답은 끝까지 읽은 문장까지만 기록하고 "(끊김)"을 붙입니다.
- **서버 대기 중 이어 말하기**: 진행 중인 요청을 버리고 앞말과 뒷말을 합쳐 다시 보냅니다(`chat/amend`). 이것으로 `useKiosk.ts:197` 버그도 고칩니다.
- **빠른 길 (팀장 결정 필요 ①)**
  - 인원·맵기·종류 중 조건 하나만 담긴 확정 발화나 답 버튼이면, 서버 없이 조건을 반영하고 다음 빈 조건을 템플릿으로 묻습니다.
  - 인원과 (맵기 또는 종류)가 채워지면 그때 LLM을 부릅니다(추천 턴). 기존 `parse.ts`를 재사용하고, 판단은 클라이언트에서 합니다(Render 왕복과 잠든 서버 깨우기를 피함).
  - 중간 인식 결과로는 확정하지 않습니다.
- **맞장구**: "네!", "좋아요, 골라 볼게요" 같은 고정 문장은 키오스크가 시작할 때 `/api/tts`로 미리 받아 브라우저 메모리에 둡니다. 추천 턴의 대기 시간을 이것으로 가립니다.
- **서버 깨우기**: 화면이 열려 있는 동안 10분마다, 그리고 시작 화면에 들어올 때 `/api/health`를 부릅니다.
- **2회 실패 시**: 6초 동안 말이 없으면 "버튼으로 골라도 돼요"라고 안내합니다. 두 번 실패하면 터치 답 위주로 바꿉니다.

### 4-2. 서버 (`/api/chat`)
- **응답 추가 필드** (`picks: string[]`는 호환을 위해 유지):
  ```ts
  pickReasons: { id: string; why: string; heard: string | null; review: string | null }[] // 순서 = 순위
  heardSummary: string | null   // 30자 이하, 서버가 조건으로 만듦
  partyAssumed: boolean
  ```
  - **why**: LLM이 씁니다. 40자 이하, 물음표 금지(있으면 조건 기반 기본 문구로 바꿈).
  - **heard**: LLM이 손님 말에서 인용합니다. 서버가 user 턴에 실제로 있는 20자 이하 구절인지 확인하고, 아니면 null로 바꿉니다.
  - **review**: 서버가 `reviewQuote`로 채웁니다.
- **pick 검증**: 품절, 제외 재료(해산물 묶음 포함), spicy=0인데 매운 메뉴인 경우를 뺍니다. 프론트 `allowed()`와 같은 규칙입니다.
- **guard()**
  - 인원을 말한 적이 없는데 done이면 추천을 막고 인원을 묻습니다. 판단은 user 턴에서 `partyMentioned`로 합니다.
  - 강제 종료 때는 1명으로 하고 `partyAssumed:true`를 보냅니다.
  - done인 답에 '?'가 있거나 거른 메뉴 이름이 들어 있으면 템플릿 문장으로 바꿉니다.
- **속도**: `maxOutputTokens`를 설정합니다. Gemini `thinkingConfig`는 설정(`GEMINI_THINKING`)으로 두고 실측합니다. temperature는 0.3으로 낮춥니다. Claude는 `max_tokens`를 1024로 줄입니다. 로그에 경로(fast/llm)와 시간(ms)을 남깁니다.
- **프롬프트**: 첫인사 지시와 날씨 예시를 지우고, 중복 규칙을 정리합니다. 메뉴 목록은 그대로 둡니다(나누기는 실측 뒤에).

### 4-3. 추천 엔진 (`KioskAI.recommend`)
- 가점 방식을 버리고, **picks 순서대로 1~n번 자리를 먼저** 채웁니다. 수량과 곁들임은 기존 `build`가 정합니다.
- 남은 자리만 기존 정렬로 채웁니다.
- 규칙 엔진은 검증(제외 재료, 품절, 예산, 과다 수량)과 picks가 비었을 때의 대체만 맡습니다.
- `reasons[0]`은 "‘{heard}’라고 하셔서 {why}"입니다. heard가 없으면 why만 씁니다.

### 4-4. 화면 (팀장 결정 필요 ②)
- **새 통합안 `?rec=d`**: 안1을 뼈대로 하고, 안3의 "이해한 것"을 한 줄 칩으로, 안2의 카드를 보조 터치 답으로 합칩니다. a/b/c는 비교용으로 남깁니다.
- **상태 표시 4가지** (아바타 테두리와 `role=status` 문구로, 색만으로 구분하지 않음)
  - 직원 말하는 중: "말씀하시면 멈춰요"
  - 듣는 중: 파형과 실시간 자막
  - 생각 중: 1초 뒤에 표시, 4초가 넘으면 "메뉴 찾고 있어요"
  - 마이크 꺼짐
- **"눌러서 대답하기" 큰 버튼은 없앱니다.** 남기는 것: 보조 터치 답, "아무거나 추천", "메뉴판", "마이크 끄기".
- **결과 화면**
  - 맨 위: 직원 말풍선 "‘둘이서 안 맵게’ 하셨죠?"와 조건 칩(누르면 고치기, `partyAssumed`면 "1인 기준" 칩)
  - 1순위: 큰 카드(사진, 수량, 가격, 인용 이유, 리뷰 한 줄, 전폭 "이걸로 담기")
  - 2·3순위: 한 줄씩
  - 버튼은 "더 이야기하기"와 "메뉴판" 두 개만
  - 큰 글씨 모드에서는 1순위만 보여 줌
- **지표**: 시작부터 담기까지 걸린 초, 터치 수, 턴 수, 턴당 대기(ms), 끼어들기 횟수. 숫자만 기록하고 문장·음성은 저장하지 않습니다(D2).

### 4-5. 회귀 평가 세트 (Byte by Yum!의 합성 대화와 자동 채점을 가볍게 가져옴)
- 손님 페르소나 20명의 대본으로 배포 서버를 실제로 부르는 스크립트를 개발용으로만 둡니다(CI 아님, 무료 한도 주의).
- 규칙 채점: 질문과 asking 일치, 60자 이내, 제외 재료 위반 0, 인원 미확인 추천 0, 추천 답에 물음표 0, 완료까지 턴 수, picks와 1순위 일치.

## 5. 대안과 선택
| 쟁점 | 고려한 안 | 선택 / 이유 |
|---|---|---|
| 추천 주체 | LLM picks 우선 / LLM은 조건만, 추천은 규칙 엔진 | **picks 우선 + 규칙은 검증만**: 지적 4를 정면으로 해결. 규칙 엔진은 안전장치로 남김 |
| 빠른 길 위치 | 서버(로직 한 곳) / 클라이언트(왕복 없음) | **클라이언트**: 잠든 서버와 왕복을 피함. 서버는 템플릿 턴이 포함된 전체 기록을 받으므로 문맥이 이어짐 |
| 첫인사 | 서버 템플릿 / 화면 고정 문구 | **화면**: 서버 대기 0 |
| 지연 | SSE 스트리밍 / 맞장구 + 빠른 길 | **맞장구 + 빠른 길 먼저**: p95가 3초를 넘으면 SSE |
| 에코 | VAD + ducking 4중 / 텍스트 대조 + 터치 | **텍스트 대조 + 터치 (1차)**: 별도 VAD를 동시에 여는 것은 실기기 실측 뒤에 |

## 6. 팀장 결정 (2026-11-03)
1. **빠른 길은 넣지 않습니다.** 모든 대답은 AI가 만듭니다(D99 유지). 4-1의 "빠른 길" 항목은 빼고, 속도는 맞장구 미리 받기, 서버 설정(출력 제한·thinking·temperature), 서버 깨우기로 줄입니다.
2. **화면은 기존 a/b/c나 통합안 d가 아니라, Yum의 디자인 아이디어로 새 3안을 아티팩트로 만들어 팀장이 고릅니다.** 4-4의 화면 구성은 그 선택으로 바뀝니다. 다만 상태 4가지와 결과 화면 필드(인용 이유, 담기 1터치, "1인 기준" 칩)는 어느 안이든 공통입니다.
3. 나머지 1차 범위는 구현을 시작합니다.

## 7. 테스트 순서 (TDD, 먼저 실패할 것)
- **backend**: 첫인사 미생성(turns가 assistant로 시작), done 답의 '?' 교체, 인원 미확인 추천 차단, "혼자 왔어요"는 1명 확인, 위반 pick 제거(품절 포함), heard 검증·why 40자·review 채움, 전부 걸렸을 때 처리, maxOutputTokens·thinking 전달
- **frontend 단위**
  - picks가 키워드·종류가 높은 메뉴보다 1순위, reasons[0] 인용 형식, 위반 pick 제외
  - 말끝 타이머(어미별 ms)
  - barge-in(자기 문장과 같으면 무시, 다르면 멈춤)
  - 빠른 길 판정
  - chat/amend
- **frontend 화면**: 말하기 버튼 없음과 상태 문구, 서버 대기 중 고정 첫인사, 대기 중에 말해도 확인 화면으로 가지 않음, 1순위 카드 인용·담기 1터치, "1인 기준" 칩
